FaceTry 人才招聘工作台 · 开发要求

在现有 AI 面试辅助工作台基础上，按 PRD V1.1 重新设计内部业务模块和页面；后端全面改为 Python，接入 MySQL 与 MinIO，配置统一走 .env。

01

项目定位

在现有 FaceTry「AI 面试辅助工作台」基础上，按 PRD V1.1 重新设计内部业务模块和页面，将其扩展为「人才招聘工作台」：承接简历入库之后的招聘业务，覆盖数据库读取 → AI 辅助筛选 → HR 跟进 → 约面与通知 → 面试评价 → 确认录取后的飞书审批 / BPM 录取流程衔接。

  • 仓库地址：http://192.168.18.190:9880/ailab_livzon/facetry（所有开发基于此仓库分支进行）
  • 数据获取已独立：前程无忧、猎聘、BOSS 等渠道由影刀（RPA）采集并写入来源数据库，工作台只读来源数据库，不开发任何爬虫、不直连招聘网站、不负责影刀调度。
  • 自动录制、自动纪要本期不做；数据看板最后做（P2）。
02

不可变更项（硬性约束）

  1. 首页与登录页保持不变。现有 src/views/Home.tsx、src/views/Login.tsx、src/views/LoginShowcase.tsx 的页面结构、视觉与交互不改动；登录入口、飞书 OAuth 跳转流程（api/auth/feishu）维持现状。本次只重构登录之后的内部业务页面。
  2. 飞书应用配置不变。继续复用现有飞书自建应用，FEISHU_APP_ID / FEISHU_APP_SECRET / FEISHU_REDIRECT_URI 的取值与应用本身不变；新增的飞书能力（日历、会议、审批）在同一个应用下申请权限即可，不得新建应用替换。
  3. 已有 AI 面试助手能力保留复用：简历解析与原文定位、提纲生成、题目生成与编辑、逐题打分、备注、综合评价、题库管理（server/prompts.js 的提示词体系与既有交互流程）作为面试官侧评价能力的基础，Python 后端重写时功能对齐、不阉割。
03

技术栈调整

层现状目标
前端React 19 + TypeScript + Vite + Tailwind CSS 4不变，继续沿用 src/ 现有工程
后端Node.js 原生 http（server/server.js）全面改为 Python（建议 FastAPI + Uvicorn），Node 后端在新后端验收后下线
业务数据库node:sqlite 本地文件MySQL（业务库）；同时按约定只读接入来源数据库（影刀落库，类型与结构待采集侧提供样例后确认）
文件存储服务器本地磁盘MinIO（简历附件、原材料等对象存储）
配置config.json + 环境变量全部改为 .env 环境变量，见第 8 节

Python 后端要求

  • Python ≥ 3.11，建议结构：app/（routers / services / models / schemas / core）分层，ORM 用 SQLAlchemy 2.x + Alembic 管理迁移；HTTP 框架建议 FastAPI（自动生成 OpenAPI 文档）。
  • 接口风格与现有前端 src/api.ts 的约定保持一致（/api/... 前缀、错误体 { "error": "中文提示" }），使前端切换后端时改动最小；确实需要调整的接口在 PR 中逐条说明。
  • 异步任务（AI 解析、出题、评价、审批状态轮询）保留现有「Job 轮询」模式，可用后台任务 / Celery / RQ 实现，接口语义与 api/jobs/{id} 对齐。
  • 现有 LLM 调用约定不变：LLM_BASE_URL / LLM_API_KEY / LLM_MODEL，OpenAI 兼容协议。
  • 会话与权限：沿用现有 Cookie 会话 + 飞书 OAuth 登录、管理员 / 超级管理员 / 按组织授权的模型，Python 侧等价实现。
04

业务模块重新设计

按 PRD 模块 A/B/C/D 划分，模块间以候选人（Candidate）与岗位（Job/Position）为核心实体串联。

模块 A · 数据接入与人才管理（P0）

  • A1 来源数据库接入：定时 + 手动触发读取来源库中的候选人、岗位关联、渠道来源、简历与附件信息；按来源唯一标识做幂等建档，重复读取不重复建人；来源侧更新不得覆盖工作台已确认的业务数据（阶段、面评、审批结果）；记录每次同步的最后成功时间与异常。
  • A2 简历与附件展示：附件原件从来源库约定的位置同步到 MinIO 后展示；区分「候选人原件 / 平台模板文件 / 附件缺失」三种状态；附件缺失仅展示状态，不自动回网站补采。
  • A3 AI 辅助初筛：按岗位要求做宽松匹配，输出推荐理由与疑点，推荐人选优先展示；未推荐及信息不完整记录仍可在列表中人工查看；AI 结果仅为参考，是否联系由 HR 决定，AI 不自动淘汰。
  • A4 共享人才库与跟进：候选人阶段管理（新入库 / 筛选中 / 待联系 / 约面中 / 面评中 / 待录取 / 已完成 / 搁置等）、负责人分配、沟通跟进记录、下一步动作；团队共享、跨岗位复用；来源数据与工作台业务记录分表维护。

模块 B · 约面与评价（P0）

  • B1 统一约面：工作台内发起面试，关联候选人、岗位、轮次、面试官、时间与方式（线上/线下）；支持改期与取消并保留历史；重复提交不产生重复预约（幂等）。
  • B2 飞书日程与候选人通知：凡是涉及飞书会议 / 日程预约的能力，统一走飞书开放平台 API（复用现有飞书应用凭证），为面试官创建日程与线上会议，支持改期与取消同步；候选人侧的通知（短信、邮件）需要额外接入第三方通知服务（服务商待定，配置化接入），至少打通一个通道，保留预约、发送、确认状态；通知失败进入可处理队列，可重试。短信与邮件的通知模板在开发时由业务方提供，模板渲染按占位符变量设计，模板内容配置化、不写死在代码里。
  • B3 面试评价：复用已有题库、逐题打分、备注能力；AI 可依据实际评分与备注辅助生成综合评价草稿，须经面试官 / HR 人工确认后保存；无纪要不阻断评价提交。
  • B4 面试助手完善（P1）：通用题库 + JD 题 + 简历定位题的深度整合，题目编辑、隐藏恢复等体验完善。
  • B5 BPM 岗位信息同步（P1）：按已批准岗位同步名称、职责、要求，生成岗位草稿；与录取审批是两个独立对接，不互为前置。

模块 C · 录取流程与审批（P0）

  • C1 发起录取申请：业务确认录取意向后，由有权限的 HR 显式提交；申请关联岗位、候选人、面评结论及公司要求的申请材料；AI 初筛与面评均不得自动触发审批。
  • C2 飞书审批对接：按公司现有审批定义发起申请，保存审批实例标识，主动查询 + 事件回调双通道更新状态，关联回候选人。
  • C3 BPM（内部 OA）对接：发起或关联 BPM 录取流程，传递约定字段，保存流程编号与状态。
  • C4 审批进度与异常：两套系统分别展示 发起 / 处理中 / 通过 / 退回 / 拒绝 / 撤销；失败可重试但不重复发起（幂等键）；任一必需审批未完成不得标记为整体通过；两套审批的串并联关系、必经节点、最终结论来源由 HR 与流程负责人确认后配置，代码不得写死。

模块 D · 数据看板（P2，最后建设）

  • 岗位进度统计、阶段转化漏斗、渠道效果分析、招聘成本展示；财务数据接入另依权限评审。一期不开发，但业务表设计需为后续统计预留字段（渠道标识、阶段流转时间、负责人等）。

06

数据库设计要求

  • 业务库使用 MySQL 8.x，InnoDB、utf8mb4；所有表带 created_at / updated_at；核心业务记录（候选人阶段、约面、面评、审批申请）只做状态流转与追加历史，不做物理删除。
  • 幂等设计：候选人以来源库 source + source_id 建唯一约束；约面、审批申请带幂等键 / 去重约束。
  • 来源库与工作台业务库写入权限分离：工作台对来源库只读（连接串独立配置）；工作台不回写来源库，除非双方明确约定。
  • Alembic 迁移脚本随代码提交，禁止手工改库。
07

接口与外部对接要求

对接方要求
来源数据库只读账号 / 授权视图；表结构、唯一标识、更新时间、删除失效语义、附件访问方式待采集侧提供样例后确认；同步任务可配置间隔，失败可见、可重跑
飞书（日历 / 会议 / 审批）复用现有应用凭证；会议与日程预约一律走飞书开放平台 API（创建日程、线上会议、改期、取消、忙闲查询）；审批定义 ID、控件映射做成配置项；状态更新支持轮询 + 回调
BPM接口地址、认证方式、字段映射、流程定义均配置化；联调前以 mock 适配层开发，接口契约单独文档化
短信 / 邮件通知需额外接入第三方服务（短信服务商、SMTP / 邮件服务），飞书 API 不承担候选人侧的短信与邮件发送；至少一个通道可用，通道选择配置化，发送失败进重试队列；通知模板在开发时由业务方提供，按占位符变量渲染，模板内容可配置、可调整，不硬编码
LLM沿用 OpenAI 兼容协议与现有提示词资产（server/prompts.js 迁移为 Python 模块）
所有外部对接的异常（超时、权限失效、风控、状态滞后）必须显式展示并进入可处理队列，不得静默吞错。
08

配置管理（.env）

所有配置一律通过 .env 环境变量读取，代码中不得出现任何硬编码的连接串、密钥、地址。 具体值本次留空，仅提供 .env.example 模板；.env 必须加入 .gitignore，真实密钥不得提交版本库。

.env.example 需包含以下分组（值留空）：

# ---- 服务 ----
APP_HOST=
APP_PORT=
APP_ENV=            # dev / prod
SECRET_KEY=         # 会话签名密钥

# ---- 业务库 MySQL ----
MYSQL_HOST=
MYSQL_PORT=3306
MYSQL_USER=
MYSQL_PASSWORD=
MYSQL_DATABASE=

# ---- 来源数据库（影刀落库，只读）----
SOURCE_DB_TYPE=     # mysql / mssql / postgresql ...
SOURCE_DB_HOST=
SOURCE_DB_PORT=
SOURCE_DB_USER=
SOURCE_DB_PASSWORD=
SOURCE_DB_DATABASE=

# ---- MinIO 对象存储 ----
MINIO_ENDPOINT=
MINIO_ACCESS_KEY=
MINIO_SECRET_KEY=
MINIO_BUCKET=
MINIO_SECURE=false

# ---- 飞书应用（沿用现有应用，值不变）----
FEISHU_APP_ID=
FEISHU_APP_SECRET=
FEISHU_REDIRECT_URI=

# ---- 飞书审批 / BPM 录取流程 ----

# ---- LLM（OpenAI 兼容）----

# ---- 管理员（同现有 config.json 语义）----

09

非功能要求

  • 数据一致：重复同步不重复建档；来源更新不覆盖已确认业务结果；读取失败展示最后成功时间与异常。
  • 权限：按岗位 / 部门 / 面试分配限制简历与附件访问；个人信息与录取材料按公司权限展示；候选人不可见任何内部评价与审批意见。
  • 可用性：HR 日常操作路径简短；列表、详情、待办足以支撑业务运转，不依赖看板。
  • 可扩展：新增渠道只影响采集侧与来源库结构适配，工作台业务主流程与渠道数量解耦。
  • 部署：提供新的 Dockerfile / docker-compose（app + MySQL + MinIO），前端构建产物由 Python 服务托管或经 Nginx 反代，接口路径约定不变。

11

开发纪律

  1. 所有开发基于仓库 http://192.168.18.190:9880/ailab_livzon/facetry 的功能分支进行，PR 评审后合并。
  2. Node 旧后端（server/）保留至 Python 后端通过前置阶段验收，之后标记废弃；前端不得同时依赖两套后端。
  3. 每次提交附带 Alembic 迁移与必要的接口说明；.env、密钥、候选人真实数据一律不入库。
  4. 两套审批的关系、来源库结构、通知通道等「待确认事项」以配置项与适配层隔离，确认前用 mock 实现，不阻塞主流程开发。
